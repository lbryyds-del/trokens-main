# 单文本版本与 GPU 3 训练耗时排查（2026-10-23）

本页为历史阶段记录。此后 fast 配置改为 5×8、选择性 MLP/聚合 checkpoint，
损失明确简化为 global+base；当前结果见[双卡验证记录](text_concat_speed_2gpu.md)。

## 结论

最大的开销是可训练分支的反向（包括完整块 checkpoint 重算），其次是冻结
DinoTxt 视觉编码；不是文本编码，也不是 BiMHM。完整块 checkpoint 用重算换显存，
因此显存占用低不意味着计算少。每个 episode 的 35 个视频都走 5 个候选类分支，
共 175 份时空编码；每份仍有 8×256 个视觉位置。

默认 2 类×4 视频分块，每个 episode 有 ceil(5/2)×ceil(35/4)=27 个编码块；
实测前向 27 次、反向重算又 27 次。5×4 将其减为 9+9 次，数学目标不变。

## 测试条件与边界

- 物理 GPU 3，A100-PCIE-40GB，PyTorch 2.0.1+cu117，单进程，FP16。
- 真实 SAV 数据和本地冻结 DinoTxt；B=35,K=5,T=8,N=256,D=1024。
- seed=1，每次更新累计两个 episode；每组 4 次成功更新，去掉第 1 次预热，
  表内为后 3 次更新均值除以 2，单位是秒/episode，不是秒/optimizer update。
- 固定第一个真实 episode 重复计算以隔离计算耗时；另做 8 个连续新 episode 的检查。
- 最初 GPU 3 有其他用户任务，共卡时约 3 秒/episode。此组及共卡状态切换组
  **不用于最终提速比例**；主表是在 GPU 3 空闲后复测的结果。
- 未保存训练 checkpoint，未运行正式 epoch，未停止/修改任何现有进程。
- 这里不包括多卡 DDP 通信、完整训练指标和长时间数据加载波动，不应直接换算双卡 epoch ETA。

## 单文本默认 2×4 分块的阶段计时

| 阶段 | 秒/episode | 约占前向+反向时间 |
| --- | ---: | ---: |
| 可训练部分反向，含 checkpoint 重算 | 0.711 | 50% |
| 冻结 DinoTxt 视觉编码，280 帧 | 0.463 | 32% |
| 候选类时空编码前向，含 Norm/聚合 | 0.215 | 15% |
| 文本读取、投影及归一化，缓存命中 | 0.004 | 0.3% |
| 其余前向/损失等 | 约 0.031 | 约 2% |

反向的 0.711 秒中，约 0.214 秒是编码块重新前向，**已经包含在反向总量中，不能再次相加**。
BiMHM 前向约 0.00013 秒/episode。原未缓存文本约 0.024 秒/episode，
因此缓存有帮助，但不是主要提速来源。

CUDA 是异步执行的：CrossMotion 的 CPU 包围计时约 0.46 秒/episode，
但 GPU 区间仅约 0.012 秒。其可见性断言触发同步，等待了前面已经排队的视觉计算；
不能把这段 CPU 等待再归因于 CrossMotion 算力，更不能与视觉耗时重复相加。

## 分块对照

以下三组不启用阶段插桩，均为单文本、文本缓存、完整块 checkpoint：

| 类别×视频分块 | 前向+反向秒/episode | 整步墙钟秒/episode | 峰值 allocated GiB |
| --- | ---: | ---: | ---: |
| 2×4 | 1.423 | 1.433 | 10.15 |
| 5×4 | 1.352 | 1.362 | 12.09 |
| 5×8 | 1.345 | 1.356 | 15.36 |

5×4 相对 2×4 耗时下降约 5.0%；5×8 相对 5×4 只再降低约 0.5%，
却增加约 3.27 GiB allocated。因此提供 `configs/trokens/sav_text_concat_s1_fast.yaml`
采用 5×4，默认 `sav.yaml` 保留 2×4 作为对照。fast 配置只改类别分块与输出目录。
所有成功检查均无非有限梯度、无 AMP 跳步，分类头和主编码器实际更新。
分块改变浮点归约/矩阵计算形状，后续参数轨迹不保证逐位相同；并非效果提升实验。

另用 5×4 连续读取 8 个新 episode，后 3 次更新平均墙钟约 1.366 秒/episode，
DataLoader 等待约 0.0104 秒/episode（4 workers，已预热），峰值 allocated 约 12.09 GiB。
这支持“本次单卡短测的数据等待不是主瓶颈”，不能证明所有 epoch、两卡或冷缓存 I/O 都没有瓶颈。

原 32 份文本版本的阶段插桩复测为约 1.519 秒/episode（前向+反向），
单文本+缓存同样插桩为约 1.424 秒/episode，约减少 6.3%。二者同时改变 token 数和缓存，
不是纯缓存收益，也不能将空间 QK 元素数减少 20.3% 解释为整网快 20.3%。

## 为什么暂不关闭全部 checkpoint

在同样真实尺寸、2×4 分块下关闭完整块 checkpoint，首次前向就触发本次设置的
80% allocator 上限：约 30.85 GiB allocated、31.51 GiB reserved，上限 31.52 GiB，
尚未完成成功更新。这证明其内存成本显著增加，**不证明 40 GiB 整卡必然放不下**。
没有继续占满整卡，也没有把失败配置设为默认。

若还要更明显地提速，下一步值得单独实现并对照的是选择性 checkpoint：
只重算 MLP/聚合、保留部分注意力结果；当前 concat 路径尚未接入，不能直接套用旧 early-route 开关。
需要测前向/梯度等价性、全尺寸峰值和吞吐后再启用。降低帧数/轨迹数、关闭损失不是本次优化。
也不能直接缓存每个视频的一份视觉特征来替代所有训练视图，因为当前 RandAugment 仍开启。
